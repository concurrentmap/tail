# TAILED — Technical Architecture

Companion to [game-design.md](game-design.md). Section numbers there are
referenced as GD§n.

## 1. Stack

| Concern | Choice | Why |
|---|---|---|
| Engine | **Unity 6.5 (6000.5.2f1)**, URP | Already installed on host; URP scales to many cars + mirror render targets. |
| Language | C#; simulation core as **pure C# (netstandard2.1)** | Core is unit-testable from WSL with `dotnet test`, no editor needed. |
| Networking | **Netcode for GameObjects 2.13** as connection/transport only (one named message, byte payloads from `core/Net`); direct IP / LAN today; UGS Relay or Steam transport for NAT traversal later | Host-authoritative listen server is the friendslop norm (Lethal Company, R.E.P.O.). |
| Traffic replication | Custom snapshot channel over NGO `CustomMessagingManager` | NPCs are *not* NetworkObjects — too many, too chatty. |
| Voice | **Built in**: IMA ADPCM (64 kbps) over the game connection, host-routed | No external service/account; Vivox/Steam voice remain options. |
| Map | **Procedural fictional town** generated in `core` from a seed; meshes built at load | New town per match, no art pipeline for layouts, fully testable in WSL. |
| Physics | PhysX; custom raycast suspension for player cars | Better arcade feel and more stable than WheelCollider. |

## 2. Dev workflow from WSL

Unity runs on Windows, so the **Unity project must live on NTFS** — Unity on a
`\\wsl$` path has broken file watching and is very slow.

The repo lives at `C:\dev\vehicle_chase` (`/mnt/c/dev/vehicle_chase` from WSL);
`~/vehicle_chase` should be a symlink to it. The .NET 8 SDK is installed in
`~/.dotnet` (user-local, no sudo).

Three ways Claude (in WSL) drives Unity — all implemented and verified in M0:

1. **`tools/unity.sh`** — `compile`, `test [EditMode|PlayMode]`, `build [--dev]`,
   `open`, `core-test`. Uses the bridge automatically when the editor is open,
   otherwise runs `Unity.exe -batchmode` via WSL interop (logs in `out/logs/`,
   compiler errors echoed on failure, NUnit XML summarised).
2. **Editor bridge** (`unity/Assets/Tailed/Editor/Bridge.cs` + `tools/bridge.sh`)
   for when the editor is open (batch mode refuses an open project). The editor
   polls `unity/Temp/Bridge/inbox/*.json` and answers in `outbox/`; a heartbeat
   file shows it's alive. Commands: `ping`, `status`, `refresh` (returns compile
   errors), `play`, `stop`, `run-tests <mode>`, `screenshot` (→ `out/screens/`,
   readable by Claude), `console [n]`, `execute <Type.Method>`, `quit`. Async
   commands survive domain reloads via `SessionState`. File-based on purpose:
   WSL is in NAT mode, so localhost sockets don't cross cleanly, but `/mnt/c` does.
   Disabled in batch mode.
3. **`dotnet test`** on `dotnet/Tailed.sln` — the fastest loop (~6 s) and where
   most traffic/rules logic gets developed.

Built player: launch several instances via `cmd.exe /c start` with
`-screen-width 960 -screen-height 540 -tailed-autojoin` flags for local
multiplayer smoke tests.

## 4. Town generation & rendering

Everything is derived from one seed, deterministically, on every machine — so
in multiplayer only the seed is sent, never map data.

```
seed ──► TownGenerator (core) ──► RoadNetwork ──► LaneGraph (core)
                                     │                 │
                                     ▼                 ▼
                           TownBuilder (Unity) ── LaneDebugView (F1)
                           meshes built at load
```

- **`TownGenerator`**: a 16×16 lattice of 100 m cells. Every 4th line (and the
  boundary) is a straight **arterial**; other lattice points are jittered for
  irregular local streets. Cells get districts (downtown centre, industrial
  corner, 2×2 parks, suburbs elsewhere). Local streets are thinned per district
  (downtown 0%, suburbs 30%, industrial 55%, park interiors 100%) under two
  constraints: the network stays connected, and no dead ends are created.
- **`RoadNetwork`**: nodes, edges (class: arterial = 2 lanes/dir, local = 1),
  cells with corner nodes and per-side edge (or none, if merged into a block).
- **`LaneGraph`**: right-hand traffic. Per junction: setbacks, lanes per edge
  (kerb → centre), turn connectors as cubic Béziers (rights from the kerb lane,
  lefts from the inner lane, straights lane-to-lane), pairwise conflicts
  (crossing or merging paths), control (signal at arterial crossings and
  downtown 4-ways; priority with side-road stops at arterial/local; all-way stop
  at local 4-ways) and two-phase signal plans. Tested invariant: the lane graph
  (connectors + lane changes) is **strongly connected** for every seed.
- **`TownBuilder`** (Unity): roads are negative space — one asphalt slab, with
  kerbed sidewalk polygons (cell quads inset per side by road half-width) and
  lots raised on top. District builders place pastel downtown blocks with window
  bands and shopfronts, gabled suburban houses facing their street, warehouses
  with roller doors, low-poly trees; markings, stop signs and signal gantries
  come from the lane graph. ~6 meshes, one material: a handful of draw calls.
- **Look:** `Tailed/Toon` (vertex colour, soft-stepped sun, cool shadow tint,
  SSAO, faint rim) and `Tailed/GradientSky`; exponential haze matched to the sky
  horizon. Scene is generated by `TownSceneSetup` (bridge `execute`).
- **Dev views** (`DevViews`, keys 1–5 or bridge `execute`): Overview, Downtown,
  Suburb, Industrial, Street (driver's-eye), Junction (top-down); R = next seed.

Polish layer (all generated from the seed):
- **Traffic lights:** every signalised approach has a far-side mast arm with a head
  over each lane (what you see while stopped) and a near-side post head at eye level;
  yellow-bordered backplates, visors, round lamps. Lamp colours live in one
  non-static mesh updated from the sim (static batching once froze them).
- **Streets:** every lattice line has a name (arterials `Main St`/`Harbor Ave`,
  locals `Maple Rd`/`Wren Ln`); green name blades at junctions, labels on the map,
  current street in the HUD. Kerb corners are rounded (6 m).
- **Furniture:** street lamps (heads glow and throw light pools at night), downtown
  planters, stop signs with lettering, landmarks — a clock tower plaza downtown and a
  water tower with the town's name.
- Characters, tyres and body edges use smooth-shaded geometry; 4× MSAA + SMAA.

Next: cul-de-sacs (bulb geometry), gentle curves/hills, chunked meshes.

## 5. Traffic simulation (host only)

The single most important system (GD§9). Runs entirely on the host inside
`core/Traffic`, stepped from Unity's `FixedUpdate` at **20 Hz**; views
interpolate.

### 5.1 Vehicle state (struct-of-arrays)
`laneId, s (arc length), v, a, lateralOffset, laneChangeTarget, routeCursor,
driverProfileId, flags (brake, indicators, lights, hazards), mode`

`mode ∈ { OnLane, InJunction, Parking, Disrupted, Player }`.

### 5.2 Behaviour models
- **Longitudinal: IDM** (Intelligent Driver Model). Leader search walks forward
  along lane → connector → next lane up to a look-ahead distance; red lights,
  stop lines and junction-box occupancy act as virtual stationary leaders.
- **Lane changes: MOBIL** with per-profile politeness; *mandatory* changes for
  the route get urgency that rises as the turn approaches (late, sloppy
  merges emerge naturally).
- **Junctions:** signals with amber/all-red; unprotected turns use **gap
  acceptance** against conflicting connectors (critical gap per profile);
  stop signs use FIFO arrival order; don't-block-the-box reservation.
- **Routing:** A\* over links with travel-time costs refreshed from observed
  speeds every 30 s. Trips come from an origin–destination table (district
  weights by time of day); trips start/end at `ParkingSpot`s so NPCs pull into
  and out of car parks — just like the Mark does.
- **Turn signals are intent, recomputed every tick after movement:** pulling out
  (left), pulling in (right), lane change pending (signalled ~1.3 s before moving)
  or in progress, turns at real junctions from 50 m out through the whole turn;
  bends get none. Forgetting is a per-manoeuvre roll (normal/cautious always signal,
  aggressive 80%, distracted 45%). A test checks every vehicle every tick.
- **Driver profiles** (parameter distributions + quirks): `cautious`,
  `normal`, `aggressive`, `lost` (occasional wrong turn → U-turn/replan),
  `distracted` (late braking, forgets indicators). These generate the *false
  positives* the Mark has to see through.

### 5.3 Traffic Director
Host-side, knows the Mark's route (the only place that information exists
besides the Mark's client). It:
- Maintains density targets around every player (higher near the Mark).
- Spawns/despawns out of every player's view (frustum + occlusion check
  against building proxies) at parking spots or network edges.
- Injects **decoy trips**: picks nearby NPCs and routes them along a stretch of
  the Mark's predicted path (GD§9 "coincident").
- Detects gridlock (cycles of zero-speed vehicles > 20 s) and resolves out of view.

### 5.4 Level of detail
| Tier | Where | Update | Representation |
|---|---|---|---|
| 0 | < 150 m of any player | 20 Hz full IDM/MOBIL | Pooled GameObject, kinematic collider, full model |
| 1 | 150–600 m | 20 Hz, simplified leader search | Pooled GameObject, LOD mesh |
| 2 | beyond | 2 Hz mesoscopic (queue per link) | Instanced draw or not drawn |

Target: 1,000 vehicles simulated, ≤ 2 ms/frame on host CPU. Pure C# on arrays
is enough at this size; Burst/Jobs is an optimisation to reach for only if
profiling says so.

### 5.5 Player cars in the sim
Player cars are physics-driven, not simulated, but they are *inserted into the
lane occupancy index* each tick (projected onto nearest lane by position +
heading) so NPCs follow, yield to and honk at them like any other vehicle.

### 5.6 Collisions with NPCs
NPCs are kinematic on every machine. When a player car hits one, the owning
client sends `NpcImpact(vehicleId, impulse, contactPoint)`; the host flips the
NPC to `Disrupted`, runs it as a dynamic rigidbody in a host physics scene
until it settles, then re-projects it onto a lane and resumes (or pulls over
with hazards and honks — a nice attention-draw). Small visual pop at
high latency is acceptable for the genre.

## 6. Vehicle identity & plate legibility

- `IdentityService` (core): one generator for **all** vehicles — model (weighted
  by fleet rarity), colour (weighted per model), plate (fictional format, e.g.
  `ABC 1234` → 7 chars). Guarantees plate uniqueness. Player cars get identities
  from the same generator (GD§9 "identity-identical").
- `PlateMatcher` (core): the flag rule — exact model + ≥ k of 7 chars in
  position; k tunable per mode.
- **Legibility is resolution-independent.** Each frame the plate shader gets a
  legibility value `L ∈ [0,1]` from
  `f(distance, angle to plate normal, illuminance, weather, relative speed)`,
  and renders the plate glyphs with a matching blur/pixelation in plate UV
  space. A 4K monitor gives no advantage. Snapshots store the value at capture
  time. Which eye position feeds it per view is in §9.
- Plates are generated as text on a shared glyph atlas via a per-instance
  `MaterialPropertyBlock` (character indices packed into a vector) — no
  per-car textures.

## 7. Networking

### 7.0 Sessions: joining, leaving, failure
- **Join:** a client that gets no answer within 12 s returns to the menu with a hint
  (address, host in lobby, firewall/UDP port).
- **Lost host:** a client that loses the host (host quit, network drop) returns to the
  menu with a reason. The transport callback only sets a flag; teardown runs in `Update`.
- **Leaving:** `GameBootstrap.ReturnToMenu` shuts NGO down, destroys the Net object
  (host/client/replica/voice components), clears replica views and the local car, and
  restarts local NPC traffic. A new host/join then builds everything fresh.
- **In-game controls:** Leave/Close in the lobby, Leave on match-over, F10 in a match.
- **Hosting failures:** a failed host (port in use) reports on the menu.
- **Late joiners:** a Tail during the motor pool; otherwise a Spotter until the next
  round, which assigns roles afresh.
- **Players leaving mid-round:** a Tail leaving mid-round doesn't stop it. The Mark
  leaving (or the last Tail) ends the round.
- Verified with `tools/mp-test.sh join/quit` and `DevHost/DevJoinLocal/DevLeave`:
  - late join → Spotter;
  - Tail quits → round continues;
  - host quits → clients back to the menu;
  - a dead address → menu after 12 s;
  - hosting, joining, leaving and rejoining again in the same process.

### 7.1 Topology
Host-authoritative listen server (host plays too). Host owns: traffic sim,
match rules, flag/mark validation, scoring. Clients own: their
own car's physics (owner-authoritative; we trust clients — friendslop, not
esports).

### 7.2 Information hiding by construction
The server only sends each client what its role may know:
- Checkpoint list/order → **Mark's client only**.
- Player vehicles are replicated **through the same traffic channel, in the same
  ID space, with the same record format as NPCs**. There is no "isPlayer" bit on
  the wire to non-teammates. Tails' clients literally cannot tell which car is
  the Mark; the Mark's client cannot tell which cars are Tails.
- Teammate positions for the Tails' team map go on a separate team-only channel.

### 7.3 Traffic replication
Per-client **interest set**: vehicles within ~600 m of that client's car, plus
a guaranteed rear cone for every car (mirrors must never show pop-in).

- **Reliable:** `Spawn(id, identity, profileVisuals)` / `Despawn(id)` when a
  vehicle enters/leaves the interest set.
- **Unreliable-sequenced snapshots at 10 Hz**, delta-prioritised by distance:
  ```
  id u16 | laneId u16 | s u16 (5 cm) | v u8 (0.25 m/s) | lateral i8 | flags u8   = 9 B
  ```
  Clients reconstruct pose from the shared `LaneGraph` — the map *is* the
  compression. `Disrupted`/`Player` vehicles send a full quantised pose instead
  (~20 B).
- ~150 vehicles × 9 B × 10 Hz ≈ 13.5 KB/s per client. Comfortable.
- Clients buffer ~100 ms and interpolate along lane geometry (smooth through
  curves where linear pose interpolation would cut corners).
- The `lateral` byte carries the *visual* offset: lane-change offset **plus**
  lane wander and the kerb nudge of a stopped bus/van (`SimVehicle.VisualLateral`),
  so clients reproduce host-side human imperfection without extra fields. Speed
  wobble, reaction delays and stop-line distance show up through `s` and `v`.
  `VehicleView.SetPose(steerFromMotion)` yaws lane-graph vehicles toward their
  actual displacement (clamped ±14°) so lateral motion reads as steering; free
  (player) poses already carry real heading.
- Turns: `LaneGraph.PathPoint` follows a Hermite curve through the path samples (no heading steps
  between samples), and `VehiclePose` poses connector traffic like a car — rear axle on the path,
  front leading — so the body yaws smoothly into a turn. In a connector, `lateral` carries the
  driver's line (`DriverProfile.TurnLine`: cut the corner or swing wide). Per-driver turn speed
  (`TurnSpeedFactor`), braking point (`TurnBrakeLead`) and throttle roll-on (`Jerk`) vary the
  approach and exit. Test: `TrafficTests.Turns_YawSmoothly`.
- Kerb stops (`LaneGraph.KerbStops`: bus stops + loading boxes) and U-turn
  connectors (`TurnType.UTurn`, centre-most lane, non-signalled junctions, never
  used by the router or by `LaneIndex` projection) are derived from the seed, so
  both ends agree without any wire data.

### 7.4 Player car sync
Owner sends pose + velocity at 30 Hz to host; host re-emits it inside the
traffic stream to others; remote cars are extrapolated/interpolated with a
short buffer.

## 8. Match logic

`core/Rules` holds pure state machines; `Runtime/Match` adapts them.

```
Match (core/Rules): Lobby → MotorPool → Briefing → Pickup → Driving (legs ⇄ checkpoints → safehouse)
                    → Marking → Debrief (reveal, replay) → (next round | MatchOver)
```

Host-side, all in `Match` (pure C#, unit-tested):
- **Dwells:** the Mark still in a bay for N s completes a checkpoint; still
  off-road elsewhere is a dry-cleaning (fake) stop.
- **Errand marker:** `StopMarkerActive` for the first `StopMarkerSeconds` of a real
  stop → the Mark's client sets `VehicleFlags.Errand` on its car (via RouteStatus), so
  it replicates like brake lights and every client renders `ErrandMarker` on that car.
  No line-of-sight computation anywhere.
- **Flags:** validated against true identities (model + ≥5/7 plate), one token
  each, recorded as `FlagRecord`s with results hidden until the reveal.
- **Marking:** `AddPin/RemovePin` only in the Marking phase, one shared team set,
  at most `MarksAllowed` (= route length).
- **Score:** locations found (completed stops with a mark within `MarkRadius`, one
  mark per stop) vs distinct Tails identified → TailsWin / MarkWins / Draw.
- The `Debrief` message carries the outcome, per-stop and per-flag results (for the
  reveal) plus dwells, marks, timeline and trails (for the replay).

### 8.1 Bots (Autopilot + BotBrain)
Bots drive real physics cars with `Autopilot`: lane-graph routes (full length), pure
pursuit, speed from curvature, stops for red/amber lights and stop signs, obstacle
look-ahead along the steering direction, and recovery (wedged → back out; blocked by
something stationary 8 s → back out; no progress along the path for 45 s → re-plan).
Parking: `ParkAtSite(poi)` picks a free bay (physics check) and re-picks if it fills up
on the approach; leaving a bay uses its exit path; the last ~9 m is a low-speed
manoeuvre (creep in / reverse in / back out and retry), done when inside any bay of the
site. Verified with the trip harness (`DevViews.ApGoToRandomBay/ApStatus`): 8/8 trips to
random businesses 400–1200 m away parked. The traffic sim reserves a bay a player's car
is parked in (`TrafficSim.ClaimBayUnder`), so NPCs never park on players.
`BotBrain`: the Mark bot visits its route stops in order (re-parks if a stop doesn't
register) and flags the nearest car behind it at stops; Tail bots (with
`-tailed-cheat-bots`) follow the Mark, hang back ~25 m, remember where it sat still off
the road, and mark those spots in the Marking phase.

### 8.2 Art pipeline (Blender, scripted)
Models are generated by scripts, not hand-authored, so they always match the game's
dimensions:
1. `Tailed.EditorTools.ArtPipeline.WriteVehicleSpecs` (bridge) writes every model's
   dimensions and anchor points (profile, cabin, wheels, plates, mirrors, eye) to
   `tools/blender/specs.json`.
2. `blender -b -P tools/blender/build_assets.py` builds rounded "toy" vehicles to those specs
   (bevelled parts, chunky wheels, round lamp "faces", plate brackets; NPC variant with mirror
   housings, `_Player` variant without) → `Assets/Tailed/Resources/Art/Vehicles/*.fbx`.
3. `blender -b -P tools/blender/build_characters.py` builds the character kit → `Art/Characters`:
   `DriverBase`, `Eyes0-3`, `Mouth0-3`, `Hat1-8` (HatType), `Glasses1-3` (GlassesType).
- Everything is vertex-coloured. Marker colours are swapped at runtime:
  - vehicles: magenta = paint;
  - characters: green = skin, cyan = shirt, yellow = hat, blue = hat accent.
  Lamp tags ride in vertex alpha as before. Material slot 0 = body, slot 1 = glass.
- `ArtImporter` (AssetPostprocessor) keeps those FBX readable, with no materials, cameras or animation.
- `VehicleMeshFactory` uses the art when present. It clones, recolours, and appends the cockpit
  interior for the player's car; drivers are assembled per `VehicleIdentity.DriverKey` and cached.
  Otherwise it falls back to the procedural meshes.
- `VehicleIdentity` carries the driver: `Skin`, `ShirtColorId`, `Eyes`, `Mouth`, `Glasses` (+ `Hat`,
  `HatColorId`). These are replicated in the identity codec and shown on the target card.
4. `blender -b -P tools/blender/build_pois.py` builds one distinctive building per business type
   (`Poi_<Type>`, brand colour = magenta marker) plus `Prop_Canopy`/`Prop_Pump`/`Prop_Column`.
   TownBuilder places them as their own solid GameObjects on the old building line.
5. `blender -b -P tools/blender/build_town.py` builds the town kit → `Art/Town`: seven house
   variants (bungalow, two-storey, cottage, ranch with garage, A-frame, modern, gambrel), yard
   dressing (fences, hedge, mailbox, bins, toys, sheds…), car-park props (lot lamps, wheel stops,
   planters, dumpster, corrals…) and trees (round, oak, pine, poplar, blossom, bush).
   Markers: magenta = wall, cyan = roof, yellow = trim/fence, green / dark green = foliage.
   `ArtKit.Place` appends them into TownBuilder's combined meshes (colours authored as sRGB).
   Houses get invisible box colliders (`HouseSolids`). Houses/Yards/Nature/Props are emitted as
   120 m (yards 60 m) tiles so cameras, mirrors and shadow cascades cull them; yard tiles also have
   an LODGroup cull (~250 m). Tiles release their CPU copy and use Color32.
- `CockpitRig` (local car only): live steering wheel (turns with `Steer`), floating mitten hands
  in the driver's skin/shirt colours (ride the rim to ±80°, horn → hub, indicator → stalk flick),
  speedo + rev needles, dashboard bobblehead on a spring. Placed from `CarShape.Eye`: the wheel sits
  ahead of and below the eye, and the dial pod lies on the sight line from the eye through the
  wheel's upper opening, so the rim frames the dials for every model. Sculpted dash in
  `VehicleMeshFactory.AddInterior`, which also models the lower cabin: carpet, tunnel, toe board,
  pedals, handbrake, seat pedestals/cushions/bolsters, rear bench, door-card armrests and pockets,
  van bulkhead. The `_Player` body is a tub: `cut_body_top` opens the shell over the cabin and the
  glass greenhouse has no underside, so none of that is hidden.
- Vehicle lower body (`build_assets.lower_body`): dark wheel wells, swept arch flares, sills,
  door shut-lines and handles; underside floor pan, axles, struts, sump, tank and exhaust.
- Look: warm key light with softer fill (WorldEnvironment), and a colour grade per time of day
  (saturation/contrast, white balance, bloom) on the global volume. SSAO intensity 0.9 / radius 0.45.

## 9. Cockpit camera & mirrors (client)

### 9.1 Camera rig
- `DriverEye`: a transform in the cabin driven by head-look (clamped yaw/pitch),
  lean (±15 cm) and a little suspension-driven bob. It is the single source of
  "where the driver's eyes are" for both the first-person camera and mirrors.
- **First person:** main camera at `DriverEye`. Vehicle interior mesh (pillars,
  headrests, cargo walls) is rendered and occludes, so blind spots are physical.
- **Third person:** chase camera with capped height; mirror-strip HUD shows the
  mirror render textures. Main camera ≠ eye, which matters for legibility (9.3).

### 9.2 Mirror rendering (URP)
Each mirror is a quad with a `MirrorSurface` component and its own camera:
- **Reflection:** reflect `DriverEye` across the mirror plane (matrix `R`); the
  mirror camera's `worldToCameraMatrix = eyeView · R`.
- **Projection:** off-axis ("generalised perspective", Kooima) frustum through
  the mirror quad's four corners, near plane on the mirror surface — so the
  image is geometrically exact for the current head position and nothing behind
  the mirror bleeds in. Leaning changes the view for free.
- Reflection flips handedness → invert culling for mirror cameras in
  `RenderPipelineManager.beginCameraRendering`.
- The quad samples its RT with plain mesh UVs (it's a portal, not screen-space).
- **Convex** passenger mirror: widen the virtual frustum by a curvature factor
  (≈1.4×) and bake a mild barrel distortion in the mirror shader.
- Wet/dirty/vibration: mirror shader overlays + UV jitter from engine RPM/road.
- **Budget:** 3 mirror cameras on a cheap renderer asset (no shadows/post,
  LOD bias down, ~250 m far clip, Tier 0/1 layers only); RTs ~768×192 rear,
  384×256 wings; wings at 30 Hz, rear at full rate; skip any mirror not visible
  from the current view (e.g. wings when looking over the shoulder). Only the
  local player's car has live mirror cameras.

### 9.2a Mirror resolution & glances
- Each mirror measures the screen pixels it covers every frame (cockpit: projected
  corners; chase: its HUD strip) and renders at ~1.25× that (32-texel steps,
  96–2048, 2× MSAA, 0.25 s hysteresis). Mirrors off screen don't render at all.
- A **glance** (keys 1/2/3) turns the head to a mirror and sets the FOV so the
  mirror fills 72% of the view (100% with focus). This is what makes plates
  resolvable to a human on a 1080p screen — measured with `DevViews.MirrorRange` +
  `MirrorReport`: plate characters are 29 px tall at 5 m, 18 px at 10 m, 13 px at
  16 m, 9 px at 23 m behind (rear-view glance). The legibility function, not the
  pixel count, then decides the range.
- Plates render **pre-reversed in mirror cameras** (`_TailedMirrored`) unless the
  realistic setting is on, so they read normally in the mirror.
- Glyph indices reach the plate shader as `nointerpolation` attributes and are
  rounded: interpolated 16.0 arriving as 15.9999 selected the wrong atlas row.

### 9.3 Legibility per view
The plate shader computes `L` itself from two per-camera globals set in
`beginCameraRendering`: `_TailedEyePos` and `_TailedMagnification`.
- Mirror cameras: `_TailedEyePos` = the *reflected* eye = the mirror camera
  position, so the distance to the plate is the true optical path length
  (eye→mirror→plate). Magnification < 1 for the convex mirror.
- First-person main camera: the eye position, magnification 1.
- Third-person main camera: still the **driver's eye**, not the camera, plus a
  200° gaze cone around the driver's head direction: plates behind the driver are
  unreadable in chase view (only the mirror strip shows them). The cone's cosine is
  negative, so it is enabled by a separate flag (`UseGazeCone`).
- Tuning: gone beyond 57.8 m of effective distance (effective = optical distance ÷
  magnification ÷ facing ÷ visibility) — 34 m for a real-size plate × `Glyphs.PlateScale`
  (1.7; plates are 0.92 × 0.24 m). Eyesight isn't a linear fade, so plates stay crisp to
  the knee at 70% (40.5 m) and fall off fast after it. `Optics.FullAt/GoneAt` and the
  `Tailed/Plate` defaults must stay in step.
- Rendering, so screen pixels rather than a wash-out are the only limit inside the knee:
  - **SDF glyphs** (`Glyphs.SdfAtlas`, R8, spread 16 texels, built from the bitmap atlas
    with an exact EDT at startup). Thresholded, so ink stays dark and plate light at any
    size; a mip-blurred bitmap averages them to grey.
  - **4-tap rotated-grid supersampling** per pixel, each tap thresholded with a
    quarter-pixel edge: clean shapes at ~5 px glyphs, no sparkle.
  - **Gradient (anisotropic ×16) sampling** from continuous coordinates: the condensed
    glyphs are squeezed ~1.7:1, so an isotropic mip over-blurred them by about a level.
    The legibility limit is a floor on the gradients (at least 2^lod texels per axis).
  - **Optical sizing:** strokes thicken ≤ 0.12 px per side below ~10 px glyphs (more
    closes the counters of 6/8/9).
  - **Retroreflective** lighting floor (lower at night) and 75% exemption from distance
    fog; weather still acts through `_TailedVisibility`.
  - Measured at 1080p, 60° FOV, no zoom: crisp and dark at 15–25 m, marginal at 35 m
    (characters are ~5 × 3.5 px there: a pixel limit), gone by 45 m. Rear-view glance:
    crisp at 32 m.

### 9.3a Glyphs
Plate and sign lettering comes from a bold sans rasterised at runtime (built-in font →
GL → 1024² atlas, 128 px cells, mipmapped). Glyphs are drawn 1.3× wide: plates squeeze a
cell into a narrow slot (condensed plate look), signs squeeze by 0.72 (natural). The
legibility mip curve is `pow(1 − L, 0.7) × 7.2`, which kept the tested reading
distances (rear-view, focused, 1080p: crisp ≤ 10 m, readable ~16 m, gone ≥ 23 m).

### 9.3b Plate readouts (optional accessibility aid, off by default)
Superseded as the main answer by oversized plates (9.3): 1.7× plates are readable
unaided, 1080p, no zoom — direct crisp at 15 m, readable ~25–30 m, gone ~45 m;
rear-view glance readable at 32 m behind. Lamps sit outboard of the plate and a dark
bracket backs it (low noses/tails hang the plate slightly lower). The readout below
remains as a menu toggle for small screens.
Screens can't match the eye: at 72° FOV/1080p a plate 15 m away has ~5 px characters.
`PlateReadout` finds plates the driver is looking at — direct (≤10° from view centre,
facing, unoccluded by buildings/vehicles) or in the glanced-at mirror (projected through
the mirror camera onto the glass, unoccluded from the reflected eye) — and shows up to
three UI copies (`Tailed/PlateUI`) at `LegibilityLod(Optics.Legibility(...))`, the same
function and mip curve as the in-world plate. Distance/angle/weather/occlusion rules are
unchanged; only the pixel bottleneck is removed. Verified at 1080p without zoom: direct
readable 8–20 m, gone 26 m; rear-view readable to ~16 m behind, gone 23 m.

### 9.4 Snapshots & notepad
- **Snapshot:** grab the current main-view frame (including any mirror in it)
  plus the per-vehicle `L` values at that instant; stored for the flag UI.
- **Notepad:** plain text overlay, no pause.

## 10. Recording & debrief

The host samples every player car at 2 Hz during the driving phase, and `Match.Timeline`
logs replay moments: checkpoints, flags (hit/miss, who was burned), plate/car swaps,
chop-shop visits, and tags (logged by the host). Pins and stops carry their own times.
At round end one `Debrief` message carries the result, stops (with start/end times),
pins (with times), the timeline and all trails. Trails are thinned if needed to fit
`NetSession.MaxMessageBytes` (64 KB; the transport's `MaxPayloadSize` is raised from
the 6 KB default, which a full-length round's trails exceeded).

Clients replay it on the gridded map (`GameUI` debrief) on a scrubbable clock
(`ScrubBar`: play/pause, ±15 s, 1×/5×/10×/30×, click to seek, event ticks):
- trails show a faint history plus a bright last minute, with name markers at the playhead;
- stops, pins, flags and tags appear when they happened;
- a tether line joins the Mark and any Tail within 80 m;
- a live panel gives the Mark's grid square and street, and every Tail's distance.

Highlights are computed client-side from the trails: time each Tail spent within 60 m
of the Mark, closest approach (when and where), flag hits/misses and fake stops.
The debrief lasts 120 s (the host can skip).

## 11. Voice

Implemented without an external service (`Runtime/Audio/VoiceChat.cs`, codec in
`core/Net/Adpcm.cs`):
- Mic → 20 ms frames (16 kHz) → voice-activity detection → IMA ADPCM (163 bytes per
  frame, ~64 kbps while talking; every packet carries its predictor, so loss is harmless).
- Client → host `Voice` (unreliable) → host routes `VoiceOut`:
  - **team radio** (hold B): Tails/Spotters only, never the Mark; band-limited + distorted;
  - **proximity**: listeners whose cars are within 16 m (both windows down), 9 m (one), 3 m
    (none); played in 3D at the speaker's car. Y toggles windows (`VehicleFlags.WindowsOpen`).
- Playback: per speaker/channel streaming AudioClip with a 60 ms jitter buffer.
- Tests use `-tailed-test-voice` (synthetic speech, never opens the real microphone).
- Verified across 3 instances: radio frames reach the other Tail, the Mark receives none.

Also procedural SFX (no assets, `Runtime/Audio/Sfx.cs`): engine hum, two-tone horns on
every vehicle (NPCs honk at blocking players), indicator ticks, crash thumps.

## 12. Testing strategy

- **core.tests (WSL, `dotnet test`)** — IDM/MOBIL unit tests, junction conflict
  tests, plate matcher, rules state machine, snapshot codec round-trips.
- **Traffic soak scenarios** (headless, core only): run a map for 30 simulated
  minutes at max speed; assert no gridlock > 60 s, average speed within bands,
  no vehicle off-lane, red-light violations only from profiles that allow them.
  These are the regression guard for "traffic looks real."
- **Unity PlayMode tests** via batch mode: map loads, views spawn/despawn,
  replication round-trip with host + client in one process.
- **Multi-instance smoke test**: `tools/unity.sh smoke 4` builds and launches
  4 windows that auto-join and auto-drive scripted routes.

## 14. Risks

1. **Traffic that reads as real** — the whole game depends on it. Mitigate by
   building M2 first and playtesting "spot the human" with one driver among NPCs
   before any game rules exist.
2. **Client/NPC collisions** feel janky over latency — keep NPCs kinematic,
   accept host-resolved disruption; tune early.
3. **Plate legibility fairness** — keep it shader/formula-driven, never
   resolution-driven; always from the driver's eye, never the chase cam.
4. **Mirror cost** — three extra cameras per client. Cheap renderer, visibility
   culling and reduced rates; profile in M2 before traffic density is tuned.
5. **Unity↔WSL friction** — solved up front in M0 (NTFS location, bridge).
6. **Procedural sameness** — generated towns can feel samey; mitigate with
   distinct district rules, landmarks (water tower, stadium, pier) and a few
   hand-authored set pieces dropped into the lattice.
